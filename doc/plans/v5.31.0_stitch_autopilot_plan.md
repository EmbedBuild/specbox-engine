## 1. Contexto y problema

Análisis exhaustivo de la documentación oficial de Google Stitch (https://stitch.withgoogle.com/docs/, [google-labs-code/design.md](https://github.com/google-labs-code/design.md), [blog.google Stitch DESIGN.md announcement](https://blog.google/innovation-and-ai/models-and-research/google-labs/stitch-design-md/)) frente a la integración actual en SpecBox (estado v5.30.0) reveló 5 gaps que combinados causan los bloqueos recurrentes de autopilot:

| # | Gap | Síntoma observable | Severidad |
|---|-----|--------------------|-----------|
| G1 | No usamos `DESIGN.md` canónico de Google como contexto persistente del proyecto Stitch | Drift visual entre pantallas → regeneraciones manuales → autopilot rompe | **ALTA** |
| G2 | `build_site` no batch-particiona cuando UC tiene >5 pantallas | Falla silenciosa por límite duro de Stitch (5 conn screens/build) | **ALTA** |
| G3 | Sin fallback chain: si `generate_screen` falla, no reintenta como `edit_screen` ni `variants` | Pipeline se cuelga con timeout de 6 min y consume cuota PRO de más | **MEDIA** |
| G4 | Prompt template minimalista: VEG concatenado como prosa, sin estructura de capas, sin hex codes obligatorios | Primera generación sale lejos del brand → más iteración → más cuota | **MEDIA** |
| G5 | Sin tracking de cuota mensual (350 Standard + 200 Experimental) ni red de seguridad cuando se agota | Cuota Experimental se agota a mitad de mes, autopilot rompe sin diagnóstico | **MEDIA** |

**Decisión clave del usuario**: la prioridad es **calidad de diseño**, no reducir tiempo. Por tanto:
- **NO** se cambia el modelo default. `GEMINI_3_PRO` sigue siendo el default.
- El cambio Flash-default (que estaba en el análisis preliminar) queda **descartado**. Solo se introduce Flash como **red de seguridad opcional, opt-in**, cuando PRO falla por cuota o timeout terminal — para que autopilot no se rompa, no para ganar velocidad.

**Antecedentes**:
- v5.18 introdujo `stitch.py` (12 tools MCP) con timeouts de 6 min y retry exponencial.
- v3.9 introdujo VEG (Visual Experience Generation) que enriquece prompts pero los concatena como texto plano.
- v5.14 introdujo `/visual-setup` con `designMd` (~2000 palabras) en `mcp__stitch__create_design_system`.
- v5.29 introdujo documentos canónicos (`app_prd.md`, `app_spec.md`) que esta release reutilizará.

## 2. Objetivos de v5.31.0

**Largo plazo**: convertir Stitch en una capa fiable y de alta calidad sobre la que autopilot pueda iterar sin intervención humana, manteniendo el modelo PRO como default y elevando la consistencia visual entre pantallas.

**Tangibles para esta release**:

- O1. Cada proyecto SpecBox con visual setup tiene un `doc/design/DESIGN.md` canónico generado automáticamente, persistido también en el proyecto Stitch como contexto.
- O2. Generaciones multi-pantalla (>5) particionan automáticamente en batches y aplican una pasada final de "theme prompt unificado".
- O3. Cuando una generación falla (timeout, 5xx, cuota), el pipeline reintenta con la estrategia menos invasiva posible (`edit_screen` sobre baseline → `variants(REFINE)` → regenerar from scratch) antes de abortar.
- O4. Los prompts de Stitch siguen un template estructurado de 4 capas (Context / Components / Style con hex codes / Platform) y prohíben mezclar layout + componentes en el mismo prompt.
- O5. La cuota mensual de Stitch es observable en `stitch_usage.jsonl`, expuesta vía MCP, y dispara warning al 80% de consumo.
- O6. (Opt-in) Si el usuario lo activa explícitamente, una generación PRO que falla por cuota agotada o timeout terminal puede degradar a `GEMINI_3_FLASH` con marca `degraded: true` para no romper autopilot.

**Fuera de alcance** (reservado para v5.32+):
- Auto-clasificador de "pantalla trivial → Flash" — requiere dataset etiquetado, lo dejamos para una futura release.
- Component-level reuse en Stitch (feature request abierto en foro Google, depende de Google).
- Refactor de `stitch_extract_design_context` para emitir directamente DESIGN.md (compatibilidad — lo dejamos como tool legacy y el nuevo flujo usa `generate_design_md`).
- W3C DTCG export y CLI `design.md` lint/diff/export — interesantes pero no desbloquean autopilot.

### 3.2 Batching automático en multi-pantalla (G2)

**Problema**: `stitch_build_site` tiene un límite duro de 5 pantallas conectadas por llamada (confirmado por análisis de comunidad — sin doc oficial pero síntoma reproducible). Cuando un UC tiene 8-12 pantallas (típico en marketplace/dashboards), `build_site` falla con error confuso o timeout.

**Solución**: nuevo wrapper `stitch_build_site_batched` en `server/tools/stitch.py`:

```python
async def stitch_build_site_batched(
    project: str,
    stitch_project_id: str,
    screen_specs: list[dict],  # [{name, prompt, route, order}]
    batch_size: int = 4,
    apply_unified_theme_pass: bool = True,
    unified_theme_prompt: str | None = None,
) -> dict:
    """
    1. Particiona screen_specs en grupos de batch_size por proximidad funcional
       (mismo prefix de route o tag explícito 'group').
    2. Llama stitch_build_site secuencialmente por batch.
    3. Si apply_unified_theme_pass=True, al final hace multi-select sobre
       todas las screens generadas y aplica unified_theme_prompt
       (default: derivado de DESIGN.md).
    4. Devuelve {batches: [...], unified_pass: {...}, total_screens}.
    """
```

**Particionado**:
- Si `screen_specs` ≤5: una sola llamada, sin batching (compatibilidad).
- Si >5: agrupar por:
  1. Tag explícito `group` en el spec (preferido).
  2. Prefijo de `route` (`/admin/*` ≠ `/public/*`).
  3. Fallback: chunks de tamaño `batch_size` en orden de `screen_specs.order`.

**Pasada de tema unificado**: si `apply_unified_theme_pass=True`, después de generar todos los batches, una llamada extra a `stitch_edit_screens` con `screen_ids: [todos]` y prompt:

> "Standardize headers, navigation, footer, and primary buttons across all selected screens to match {DESIGN.md component patterns}. Preserve content and layout of each screen."

Esto cuesta 1 generación adicional pero garantiza consistencia visual cross-batch.

**Telemetría**: cada batch loguea `{batch_index, screen_count, duration_ms, status}` en `stitch_usage.jsonl`.

**Integración en `/plan`**: Paso 2.5b.4 reemplaza la llamada directa a `stitch_build_site` por `stitch_build_site_batched` cuando el plan tiene >5 pantallas.

### 3.3 Fallback chain inteligente (G3)

**Problema actual**: cuando `stitch_generate_screen` falla por timeout (6 min) o 5xx persistente tras 3 retries, el pipeline aborta. La política de retry actual es "regenerar from scratch", que en autopilot:
- Consume 1 más de cuota PRO.
- No aprovecha trabajo parcial (Stitch a veces devuelve resultado incompleto en lugar de error).
- Repite el mismo error si la causa es prompt-side (prompt ambiguo, conflicto de DS).

**Solución**: chain de degradación en `server/tools/stitch.py`:

```python
async def stitch_generate_screen_with_fallback(
    project: str,
    stitch_project_id: str,
    prompt: str,
    model_id: str = "GEMINI_3_PRO",
    fallback_strategy: list[str] = ["edit_baseline", "variants_refine", "regenerate"],
    enable_flash_safety_net: bool = False,  # opt-in, default OFF
    max_total_attempts: int = 3,
    **kwargs,
) -> dict:
    """
    1. Intento 1: generate_screen normal con PRO.
    2. Si falla: aplicar primera estrategia de fallback_strategy:
       - "edit_baseline": si hay screen previa con misma route/name,
         clonar y aplicar el prompt como edit_screen.
       - "variants_refine": si baseline existe, generate_variants(REFINE).
       - "regenerate": último recurso, generate_screen from scratch.
    3. Si todas las estrategias PRO fallan AND enable_flash_safety_net=True:
       último intento con GEMINI_3_FLASH, marcar resultado con
       degraded=True y warn al usuario.
    4. Si todo falla: emitir error estructurado con diagnóstico
       (qué se intentó, por qué cada paso falló, recomendación).
    """
```

**Causas de fallo y estrategia**:
| Causa detectada | Estrategia preferida |
|----------------|---------------------|
| Timeout 6 min | `edit_baseline` (si existe) → `regenerate` con prompt simplificado |
| 429 rate limit | Esperar reset (info en headers) o retry tras 60s |
| 5xx Stitch downstream | Backoff existente, ya cubierto |
| Cuota Experimental agotada | `enable_flash_safety_net=True` → Flash con `degraded: true`, **NUNCA en silencio** |
| Prompt rejected | Surface error al usuario, no auto-retry (puede ser contenido sensible) |

**Resultado degradado**: cuando se usa Flash safety net, el resultado incluye:

```json
{
  "screen_id": "...",
  "html": "...",
  "model_used": "GEMINI_3_FLASH",
  "degraded": true,
  "degraded_reason": "PRO quota exhausted (Experimental: 200/200 used this month)",
  "recommended_action": "Regenerate manually with PRO when quota resets on YYYY-MM-01"
}
```

Y en el HTML guardado, comentario al inicio:
```html
<!-- specbox:stitch:degraded model=GEMINI_3_FLASH reason="PRO quota exhausted" generated_at="..." -->
```

Hook `design-gate.mjs` (sin cambios) sigue dejando pasar HTML degradado, pero `/plan` y `/implement` muestran un warning consolidado al final del paso:

> ⚠️ **Stitch Degradation Notice**: 2 de 8 pantallas se generaron con GEMINI_3_FLASH como red de seguridad (cuota PRO agotada). Considera regenerar manualmente cuando la cuota se reinicie:
> - `screen_admin_dashboard.html`
> - `screen_billing_settings.html`

**Configuración**: en `templates/settings.json.template`:

```json
{
  "stitch": {
    "fallback": {
      "enabled": true,
      "strategy": ["edit_baseline", "variants_refine", "regenerate"],
      "flash_safety_net": false,
      "max_total_attempts": 3
    }
  }
}
```

`flash_safety_net: false` por defecto — el usuario lo activa conscientemente si quiere que autopilot nunca se rompa por cuota.

### 3.4 Prompt template 4-capas con hex codes obligatorios (G4)

**Problema**: el template actual ([design/stitch/prompt-template.md](design/stitch/prompt-template.md)) es minimalista, concatena VEG como prosa, no exige hex codes y permite mezclar layout + componentes.

**Solución**: refactor del template + validador pre-envío.

**Nuevo template** (`design/stitch/prompt-template-v2.md`):

```markdown
# Layer 1 — CONTEXT (≤80 words)
{screen_purpose} for {audience} on {platform}.
Part of {feature_name} flow. Previous screen: {prev_screen_or_none}.
Next screen: {next_screen_or_none}.

# Layer 2 — COMPONENTS (bullet list, no narrative)
- {component_1} (state: default | hover | active | error)
- {component_2}
- ...

# Layer 3 — STYLE (hex codes only, no color names)
Primary: {hex_from_design_md}
Background: {hex}
Text: {hex}
Spacing: {token_from_design_md}
Typography: {font_family}, sizes {h1_px}/{body_px}
Component patterns: see DESIGN.md > Components

# Layer 4 — PLATFORM
Device: {DESKTOP | MOBILE | TABLET}
Form factor breakpoints: {breakpoint_list}
Interaction model: {touch | mouse | both}
```

**Reglas obligatorias** (validadas pre-envío):
1. Toda mención de color debe ser hex (`#XXXXXX`). Validador rechaza "coral", "blue", "primary color" sin hex equivalente.
2. Layer 1 (Context) ≤80 palabras.
3. Layer 2 (Components) es lista, no prosa.
4. Prompt total ≤500 chars iniciales (excluyendo el bloque DESIGN.md si se incluye inline).
5. **Prohibido en un solo prompt**: mezclar cambios de layout (mover, redimensionar, reordenar) con cambios de contenido/componentes. Si se detecta intención mixta, el validador divide el prompt en 2 calls (primero layout, luego componentes).

**Validador**: `server/stitch_prompt/validator.py` con función `validate_and_normalize(prompt: str, design_md: dict) -> ValidationResult`. Devuelve:

```python
@dataclass
class ValidationResult:
    valid: bool
    normalized_prompt: str  # con hex codes resueltos desde design_md
    warnings: list[str]
    errors: list[str]
    requires_split: bool  # si detecta layout+components mixto
    split_prompts: list[str] | None
```

**Integración VEG**: el resumen VEG (~400 tokens) deja de concatenarse como `[VISUAL DIRECTION] {resumen}` y se mapea a campos estructurados:
- VEG.imagenes → Layer 2 (mood/sujetos como prompts de imagen específicos)
- VEG.motion → ya no va al prompt Stitch (Stitch genera HTML estático), va a AG-02 design-to-code (sin cambios respecto a hoy).
- VEG.diseño → Layer 3 (density, whitespace) referenciados como tokens de DESIGN.md.

**Tests**: `tests/stitch_prompt/test_validator.py` con casos:
- "Make the button coral" → ERROR ("coral" no es hex), normalizar a `#E8725A` desde DESIGN.md.
- Prompt de 1200 chars → WARNING (>500), sugerir split.
- "Move the FAB to bottom-right and add a settings icon to it" → `requires_split=True`, split en `["Move the FAB to bottom-right", "Add a settings icon to the FAB"]`.

### 3.5 Tracking de cuota mensual + observabilidad (G5)

**Problema**: Stitch tiene cuotas mensuales fijas (350 Standard + 200 Experimental, sin posibilidad de aumentar). SpecBox no las trackea, así que cuando se agotan, autopilot rompe sin diagnóstico.

**Solución**:

**(a) Telemetría enriquecida** en `stitch_usage.jsonl` (era `{tool, timestamp}`):

```json
{
  "ts": "2026-MM-DDTHH:MM:SSZ",
  "tool": "stitch_generate_screen",
  "project": "...",
  "stitch_project_id": "...",
  "model_id": "GEMINI_3_PRO",
  "duration_ms": 47230,
  "status": "success",  // success | error | timeout | quota_exhausted
  "error_type": null,
  "retry_count": 0,
  "screen_id": "...",
  "prompt_chars": 412,
  "degraded": false
}
```

**(b) Nuevo MCP tool**: `get_stitch_quota_status(project)` devuelve:

```json
{
  "month": "2026-05",
  "standard": {"used": 142, "limit": 350, "remaining": 208, "percent": 40.6},
  "experimental": {"used": 178, "limit": 200, "remaining": 22, "percent": 89.0},
  "warning": "experimental quota at 89% — consider enabling flash_safety_net or postponing non-critical generations",
  "reset_at": "2026-06-01T00:00:00Z",
  "summary": "PRO quota críticamente baja (22/200 disponibles). Standard saludable."
}
```

**Cómputo**: agregando `stitch_usage.jsonl` por mes calendario, contando solo entries con `status=success` y modelo correspondiente.

**(c) Warning automático**:
- En `/plan` Paso 2.5b: si `experimental.percent ≥ 80`, mostrar al usuario antes de generar y pedir confirmación.
- En `/implement` Paso 3.5.0 (advertencia costes ya existente): integrar también el % de cuota.
- Hook nuevo `stitch-quota-guard.mjs` (PreToolUse antes de `stitch_generate_screen`, `stitch_edit_screens`, `stitch_build_site`): WARNING (no bloqueante) cuando ≥80%, BLOCKING al 100% si `flash_safety_net=false`.

**(d) Heartbeat enriquecido**: añadir bloque `stitch_quota` en `.claude/hooks/heartbeat-sender.mjs` **después** del bloque de Session Continuity (que ya añadió `handoff_present`, `handoff_age_minutes`, `context_pressure` en v5.30.0). Patrón a respetar:

```js
// v5.31.0 — Stitch Autopilot: enrich payload with stitch quota state.
let stitchQuota = null;
try {
  const quotaPath = '.quality/stitch_quota.json';
  if (fileExists(quotaPath)) {
    const q = readJsonFile(quotaPath);
    stitchQuota = {
      standard_pct: q.standard?.percent ?? null,
      experimental_pct: q.experimental?.percent ?? null,
      reset_at: q.reset_at ?? null,
    };
  }
} catch { /* ignore */ }
```

Y añadir `stitch_quota: stitchQuota` al `payload` para que Sala de Máquinas lo muestre.

### 3.6 Flash safety net (opt-in, complemento de 3.3)

Ya descrito en 3.3 como parte de la fallback chain. Resumen de la API de configuración:

```json
// settings.local.json
{
  "stitch": {
    "fallback": {
      "flash_safety_net": false  // opt-in
    }
  }
}
```

Cuando `false` (default): si todas las estrategias PRO fallan, error explícito al usuario, autopilot pausa.

Cuando `true`: último recurso = Flash con `degraded: true` + warning consolidado al final del paso. Autopilot continúa.

Esto da al usuario el control: si prefiere "autopilot nunca se rompe" lo activa, asumiendo que algunas pantallas pueden salir en Flash. Si prefiere "calidad PRO o nada", lo deja en false.

## 6. Riesgos y mitigaciones

| Riesgo | Probabilidad | Impacto | Mitigación |
|--------|-------------|---------|------------|
| Stitch no expone endpoint nativo para asociar DESIGN.md a proyecto | MEDIA | MEDIO | Fallback: incluir DESIGN.md inline como prefijo del prompt en cada `generate_screen`. Costo: ~500 tokens extra/call, asumible. |
| Validador de prompts es demasiado estricto y rechaza prompts válidos del usuario | MEDIA | BAJO | Modo `validation: warn-only` por defecto la primera semana, luego `strict` si telemetría confirma <2% falsos positivos. |
| Particionado de `build_site_batched` rompe la consistencia visual entre batches | BAJA | MEDIO | Pasada de "unified theme" al final mitiga. Si no es suficiente, fallback a generación serial pantalla-a-pantalla con DESIGN.md como contexto persistente. |
| Cuota de Stitch cambia (Google modifica límites) | BAJA | BAJO | Hacer límites configurables en `settings.local.json` (`stitch.quota.standard_limit`, `stitch.quota.experimental_limit`), defaults actuales. |
| Sesiones paralelas modifican mismos archivos durante implementación | ALTA | ALTO | **Este plan se entrega como documento únicamente**. Implementación se hará después, en sesión dedicada, tras coordinar con sesiones paralelas. |
| Flash safety net produce calidad heterogénea sin que el usuario se entere | MEDIA | MEDIO | Default `false` (opt-in explícito). Cuando activo, warning consolidado obligatorio + comentario HTML + campo `degraded: true` en evidencia. |
| Refactor de prompts en `/plan` rompe generaciones reproducibles de proyectos pre-v5.31 | BAJA | BAJO | Template v2 es opt-in via flag `prompt_template_version` en settings. Default v1 hasta v5.32. |

## 8. Rollback plan

Si v5.31.0 introduce regresiones graves en proyectos en producción:

1. **Toggle global**: `settings.local.json` → `stitch.use_v2_pipeline: false` revierte a las 12 tools originales y skills v1.
2. **Per-tool toggle**: cada tool nueva (`stitch_build_site_batched`, etc.) tiene flag `enabled: true|false`.
3. **DESIGN.md generado se queda**: no se borra del filesystem, simplemente Stitch deja de leerlo (queda como documentación). No hay corrupción posible.
4. **Hot-fix release v5.31.1**: si bug específico, fix puntual sin downgrade.

## 10. Decisiones tomadas en la conversación que generó este plan

- **Modelo default sigue siendo `GEMINI_3_PRO`**. Calidad > velocidad para el usuario.
