## 1. Contexto del bug

### 1.1 Descubrimiento

El 2026-05-25, ejecutando `/discovery test_inheritance_helper` desde `specbox-control-panel` con MCP remoto (`SPECBOX_ENGINE_MCP_URL=https://mcp-specbox-engine.jpsdeveloper.com/mcp`), la tool `start_discovery` devolvió `app_market_present: false` aunque el archivo `doc/app/app_market.md` existía en el cliente con contenido real (ICPs + JTBDs reales, no template-pristine).

Síntomas observados en la sesión:
- `start_discovery(project_path=".")` → `status: "resumable"` + `app_market_present: false`. El archivo "resumable" no se materializó en disco del cliente.
- 3 invocaciones consecutivas de `validate_discovery_completeness` devolvieron el mismo `missing: [...]` sin importar lo que se escribiera localmente con Write.

### 1.2 Causa raíz

`start_discovery`, `validate_discovery_completeness`, `detect_v60_migration_case` (`server/tools/discovery.py`) reciben `project_path: str = "."` y hacen `Path(project_path).resolve()`. En MCP remoto eso resuelve contra el **CWD del proceso MCP server (VPS)**, no del cliente. Las tools operan sobre el filesystem del VPS:
- Lecturas devuelven datos del VPS (típicamente nada, o el propio repo `specbox-engine` que vive ahí).
- Escrituras crean archivos en el VPS, invisibles para el cliente.
- El validador siempre lee del VPS, nunca del cliente.

## 2. Decisión arquitectural — content-passing universal

### 2.1 Opciones consideradas

| Opción | Trade-off | Veredicto |
|--------|-----------|-----------|
| **(a) Absolute-path universal** (extender patrón v5.29 a las 17 tools) | Mínima invasión, retro-compatible. **Pero**: solo funciona en MCP local (stdio); roto en MCP remoto, contenedores, multi-tenant SaaS, claude.ai web. Resuelve el síntoma, no la causa. Sigue asumiendo "MCP comparte filesystem con cliente". | ❌ Es deuda técnica con careta de fix |
| **(b) Content-passing universal** (las tools reciben contenido por parámetro, nunca tocan filesystem) | Más cambios. **Pero**: funciona idéntico en local/remoto/contenedor/multi-tenant. Elimina la clase entera de bugs filesystem-remote. Auto-documentado en firma. | ✅ Elegida |
| **(c) Híbrido** (cat A1 content-passing, cat A2 absolute-path) | Convivencia de dos patrones, dos paths de debugging, dos cosas que mantener. | ❌ Maximiza deuda técnica |

### 2.2 Definición del patrón

**Antes (roto en MCP remoto):**
```python
@mcp.tool
def start_discovery(feature_name: str, project_path: str = ".", mode: str = "auto"):
    root = Path(project_path).resolve()
    market_path = root / "doc/app/app_market.md"
    app_market_present = market_path.exists()  # ← lee filesystem del MCP
    # ...
```

**Después (content-passing):**
```python
@mcp.tool
def start_discovery(
    feature_name: str,
    app_market_content: str | None = None,        # ← cliente provee
    existing_artifact_content: str | None = None, # ← cliente provee
    mode: str = "auto",
):
    app_market_present = app_market_content is not None and app_market_content.strip() != ""
    # ... toda la lógica opera sobre los strings, no toca filesystem
    return {
        "discovery_id": ...,
        "status": ...,
        "skeleton_content": "...",  # ← cliente escribe esto con Write
    }
```

**El cliente (skill) hace I/O:**
```yaml
# .claude/skills/discovery/SKILL.md
- Read doc/app/app_market.md → app_market_content
- Read doc/discovery/<feat>/icp_jtbd.md (si existe) → existing_artifact_content
- Call mcp__SpecBox-MCP__start_discovery(feature_name, app_market_content, existing_artifact_content)
- Write doc/discovery/<feat>/icp_jtbd.md ← skeleton_content del response
```

### 2.3 Caso especial: `run_quality_audit`

Los 8 analyzers SQuaRE necesitan escanear el código real (lint, complexity, dup, security). Mover **la lectura del código** al cliente es inviable por payload (un repo entero serializado). Solución: los analyzers se ejecutan en cliente (script local invocado por skill `/audit`), generan `QualityReport`, y se envía solo el report al MCP via `submit_quality_audit(project, report)`. Es **report-passing** en lugar de content-passing puro — la única excepción documentada.

Cada UC trae su test module nuevo:
- `tests/test_discovery_content_api.py` (UC-614)
- `tests/test_app_docs_content_api.py` (UC-616)
- `tests/test_onboarding_content_api.py` (UC-617)
- `tests/test_audit_content_api.py` + `tests/test_audit_analyzers_local.py` (UC-618)
- `tests/test_acceptance_content_api.py` (UC-619)
- `tests/test_misc_cat_a_content_api.py` (UC-620)
- `tests/test_mcp_client_io.mjs` (UC-621, Node-side)

**Cobertura mínima por tool:**
1. Caso happy path: contenido válido completo.
2. Caso vacío: contenido None o empty string.
3. Caso malformado: contenido sin frontmatter / sin marcadores zone.
4. Caso idempotencia: segunda llamada con artifact existing reconoce estado previo.
5. Caso bundle parcial: algunos archivos None, otros con contenido.

**Regresión global:** suite completa `pytest tests/` debe quedar verde. 0 regresión en tests previos no relacionados con paths.

**Test de integración MCP remoto:** smoke test manual con `SPECBOX_ENGINE_MCP_URL` apuntando al VPS — las 6 skills deben funcionar sin tocar filesystem del VPS.

## 6. Breaking changes documentados

### 6.1 API rota (intencional)

Las 17 tools cat A cambian firma. **Sin deprecation warning, sin backwards-compat opcional**. Justificación:
- v6.0 lleva <24h en main; superficie de uso externo mínima.
- Mantener compat duplica caminos de código y no resuelve el bug en remoto.
- El único consumidor real son los skills del propio engine, que se migran en UC-622 del mismo PR.

### 6.2 Skills rotas (intencional, mismas PR)

Los 6 skills (`/prd`, `/plan`, `/visual-setup`, `/app-sync`, `/audit`, `/acceptance-check`) se actualizan en UC-622. El PR final agrupa todos los UCs — no se mergea ninguno sin los otros (squash merge único).

### 6.3 Hook `freeform-path-guard.mjs` deprecado, no eliminado

El hook v5.29 sigue existiendo pero pasa a estar marcado como `@deprecated` en su header. Se elimina formalmente en v6.1 (UC futuro). Justificación: proyectos pre-v6.0.1 todavía lo necesitan para FreeForm onboarding.

### 6.4 Setting `specbox.app_docs_sync.block_on_drift` sin cambios

El hook `app-docs-sync-guard.mjs` ya opera en cliente (verifica drift antes del commit) — no toca tools MCP cat A. Sin impacto.
