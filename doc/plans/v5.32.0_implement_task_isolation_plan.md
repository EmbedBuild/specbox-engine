## 1. Contexto y problema

`/implement` ejecuta una pipeline de 10 fases (DB/Infra → Stitch → Design-to-Code → Feature → Apps Script → n8n → Integration → QA → Acceptance Tests → Acceptance Gate). El SKILL.md ya **documenta** la delegación a Tasks aisladas (líneas 469-536 + 496-506) y el aislamiento estricto del orquestador, pero ese contrato **no está mecánicamente forzado** todavía:

| # | Gap | Estado actual | Síntoma |
|---|-----|---------------|---------|
| G1 | No hay `execution_context.json` persistido | El orquestador mantiene `branch`, `feature`, `stack`, `board_id` en su contexto y los inyecta al prompt de cada Task | Si el orquestador compacta o se reinicia a mitad de UC, esos valores se pierden y el Task siguiente arranca con prompt inconsistente |
| G2 | Context budget de ~20k declarativo | CLAUDE.md y SKILL.md mencionan "max ~20k tokens" pero ningún hook lo cuenta antes de spawnear el Task | Tasks reciben prompts que en la práctica exceden el budget; cuando explotan, no hay diagnóstico — solo "context too large" |
| G3 | File ownership documentado pero no enforced | `.claude/skills/implement/file-ownership.md` declara qué paths puede tocar cada agente; ningún hook valida Write/Edit contra el ownership del agente activo | AG-01 puede escribir en `test/` o `supabase/` sin que ningún guardrail lo detecte; corrupciones cross-agent silenciosas |
| G4 | Phase deltas se capturan en contexto principal | Spec-Code Sync (Paso 5.1.1b / 8.5.1a) lee diffs vía git desde el orquestador y los persiste al PRD | Cuando una fase corre como Task aislado real, el delta queda dentro del Task y nunca llega al PRD — las "Implementation Status" sections quedan incompletas |
| G5 | No hay flag para diferenciar Task real vs inline | Cada operador interpreta libremente "delegar a AG-XX" | Imposible medir qué % de fases corren ya aisladas y avanzar la migración con datos |

**Por qué esto bloquea autopilot**: en UCs grandes (≥5 fases con 200+ archivos tocados), el contexto del orquestador se exhausta antes de llegar al Acceptance Gate. v5.30 ("Session Continuity") introdujo `/handoff` como red de seguridad — funciona, pero el handoff es reactivo. v5.32 ataca la causa raíz: cada fase debe ser autocontenida y el orquestador solo guarda punteros + outputs compactos.

**Decisión clave**: esta release **no rediseña la arquitectura** del SKILL.md — la delegación a Tasks ya está descrita. v5.32 implementa los **5 guardrails que faltan** para que esa arquitectura sea fiable y observable, y sube progresivamente el porcentaje de fases que corren aisladas mediante un flag opt-in.

## 2. Objetivos de v5.32.0

**Largo plazo**: cada fase de `/implement` corre en un Task aislado con context budget verificado, file ownership enforced, deltas estructurados que sobreviven al aislamiento, y un orquestador que no acumula contexto entre fases.

**Tangibles para esta release**:

- O1. Existe `execution_context.json` por feature con `branch`, `feature_slug`, `stack`, `board_id`, `plan_hash` — escrito al final del Paso 1, leído por cada Task delegado.
- O2. Existe un script + hook que cuenta tokens del prompt de cada Task antes de spawnearlo y rechaza (warn-only por defecto) si excede `task_budget_tokens` (default 16000).
- O3. Existe `file-ownership-guard.mjs` que valida cada Write/Edit contra el ownership del agente activo (declarado en `.quality/active_agent.json`); modo warn-only por defecto, promovible a strict.
- O4. Existe `phase_outputs.jsonl` por feature donde cada Task escribe un delta estructurado (`{phase, agent, files_created, files_modified, files_deleted, summary, duration_s, status, error}`) — Spec-Code Sync ya no depende del contexto del orquestador.
- O5. SKILL.md de `/implement` actualizado para escribir `execution_context.json` en Paso 0.4b (nuevo) y `active_agent.json` antes de cada Task (nuevo Paso 5.X.0), y para leer `phase_outputs.jsonl` en Paso 5.1.1b en lugar del git diff vivo.
- O6. Telemetría enriquecida en heartbeat (`task_isolation: {enabled, tasks_run, tasks_failed_budget, tasks_failed_ownership}`) para que Sala de Máquinas mida la migración.

**Fuera de alcance** (reservado para v5.32.x patches o v5.33+):

- Migrar el call-site del SKILL.md a usar la nueva tool `spawn_isolated_task` (introducida en esta release como wrapper opcional). El SKILL.md sigue describiendo `Task(AG-XX)` en prosa; la migración del call-site queda como patch siguiente cuando los guardrails estén verdes.
- Auto-clasificador "fase trivial → no requiere Task aislado" — empezamos forzando aislamiento para todas las fases excepto Integration (Paso 7) que sigue en línea por ser el orquestador.
- Promoción del context-budget-guard de `warn` a `strict` — decisión empírica tras 2 semanas de telemetría.
- Promoción del file-ownership-guard a `strict` — idem.
- Healing en Task aislado separado (hoy healing se ejecuta dentro del mismo Task de la fase fallida; mover healing a Task propio queda para v5.32.1).
- Dashboard "Task Isolation health" en Sala de Máquinas — la métrica está disponible vía heartbeat, la UI viene después.

## 3. Diseño técnico

### 3.1 `execution_context.json` (G1)

**Ubicación**: `.quality/evidence/{feature}/execution_context.json`. Escrito al final del Paso 1 de `/implement`, immutable durante toda la ejecución del UC (excepto `last_updated_at`).

**Schema**:

```json
{
  "schema_version": 1,
  "feature_slug": "uc-021-staff-management",
  "uc_id": "UC-021",
  "us_id": "US-04",
  "branch": "feature/uc-021-staff-management",
  "base_branch": "main",
  "stack": "flutter",
  "backend_type": "freeform",
  "board_id": "ff-xxx",
  "project_name": "talent-on",
  "project_root_absolute": "/Users/.../talent-on",
  "plan_path": "doc/plans/uc-021_plan.md",
  "plan_hash": "sha256-of-plan-md",
  "started_at": "2026-MM-DDTHH:MM:SSZ",
  "last_updated_at": "2026-MM-DDTHH:MM:SSZ",
  "engine_version": "5.32.0",
  "autopilot_level": "equilibrado"
}
```

**Helper Python** (`server/implement_context/__init__.py`):

```python
def write_execution_context(feature_slug: str, **fields) -> Path
def read_execution_context(feature_slug: str) -> dict | None
def update_last_updated(feature_slug: str) -> None
def compute_plan_hash(plan_path: Path) -> str
```

**Helper JS** (`.claude/hooks/lib/execution-context.mjs`) con la misma API expuesta a hooks.

**Validación de aislamiento**: `read_execution_context` es la **única** fuente de verdad que un Task aislado debe consultar para conocer `branch` / `feature` / `stack`. El SKILL.md indicará explícitamente que el prompt del Task NO repite estos valores en prosa — solo dice "lee `.quality/evidence/{feature}/execution_context.json`".

### 3.2 Token-counting + `context-budget-guard.mjs` (G2)

**Problema**: hoy nada cuenta tokens del prompt del Task antes de spawnearlo.

**Solución**: dos piezas.

**(a) Estimador puro** en `.claude/hooks/lib/token-counter.mjs`:

```js
// Estimación rápida ~chars/4. No llamamos a Anthropic API
// (sería async, costoso, y este conteo se ejecuta en hot path).
// La diferencia con el conteo real de tiktoken/cl100k es típicamente
// <8% para texto + código, suficiente para una guardrail con margen.
export function estimateTokens(text) { return Math.ceil(text.length / 4); }
export function estimatePromptTokens({ system, user, files = [] }) { ... }
```

**(b) Hook PreToolUse para Task** — `.claude/hooks/context-budget-guard.mjs`:

```js
// Dispara cuando el orquestador llama Task(...).
// Lee el `prompt` del payload, estima tokens, compara contra
// settings.specbox.implement.task_budget_tokens (default 16000).
//
// Modos:
//   warn   → emite stderr WARNING, exit 0
//   strict → emite stderr BLOCKED, exit 2
//
// Default v5.32.0: warn. Promoción a strict tras telemetría.
```

**Settings** en `templates/settings.json.template`:

```json
{
  "implement": {
    "task_isolation": {
      "enabled": true,
      "task_budget_tokens": 16000,
      "task_budget_mode": "warn",
      "ownership_mode": "warn"
    }
  }
}
```

`task_budget_tokens=16000` deja un margen del 20% sobre el ideal de 20k del SKILL.md para los tokens de respuesta esperados (~4k).

**Registro en `.claude/settings.json`**:

```json
{
  "PreToolUse": [
    {
      "matcher": "Task",
      "hooks": [{ "type": "command", "command": "node .claude/hooks/context-budget-guard.mjs", "timeout": 3 }]
    }
  ]
}
```

### 3.3 `file-ownership-guard.mjs` (G3)

**Pieza 1 — `.quality/active_agent.json`**: escrito por el SKILL.md inmediatamente antes de spawnear cada Task; eliminado tras el reporte. Schema:

```json
{
  "agent": "AG-01",
  "feature_slug": "uc-021-staff-management",
  "phase": "feature",
  "started_at": "2026-MM-DDTHH:MM:SSZ"
}
```

Si no existe `active_agent.json`, el guardrail asume que el orquestador está actuando — y deja pasar todo (compatibilidad con sesiones legacy).

**Pieza 2 — el hook**: PreToolUse Write/Edit. Lee `active_agent.json`, lee `.claude/skills/implement/file-ownership.md`, parsea la tabla a un mapa `agent → glob[]`, valida la ruta del Write/Edit contra los globs del agente activo. Si el agente está activo Y el path no matchea ningún glob suyo, según `ownership_mode`:

- `warn`: WARNING en stderr + exit 0.
- `strict`: BLOCKED en stderr + exit 2 + mensaje accionable: "AG-01 intentó escribir `test/foo.dart`. Su ownership es `lib/features/**`. Si necesitas tocar `test/`, repórtalo como dependencia pendiente y delega a AG-04."

**Helper**: `.claude/hooks/lib/ownership-map.mjs` parsea el `file-ownership.md` (formato Markdown table) a un objeto en memoria. Tests cubren: tabla bien formada, agente desconocido (deja pasar con warning), path con `..` (rechaza por seguridad).

### 3.4 `phase_outputs.jsonl` + delta estructurado (G4)

**Ubicación**: `.quality/evidence/{feature}/phase_outputs.jsonl` — append-only, una línea por Task completado.

**Schema por línea**:

```json
{
  "ts": "2026-MM-DDTHH:MM:SSZ",
  "phase": "feature",
  "phase_index": 4,
  "agent": "AG-01",
  "task_id": "uuid-v4",
  "duration_s": 423.5,
  "status": "ok",
  "files_created": ["lib/features/staff/staff_provider.dart", "..."],
  "files_modified": ["lib/main.dart"],
  "files_deleted": [],
  "summary": "Implementé el provider de staff con CRUD básico, integrado con StaffRepository (AG-03)",
  "tokens_used_prompt": 14823,
  "tokens_used_response": 3107,
  "healing_attempts": 0,
  "error": null
}
```

**Cómo se escribe**: cada Task termina con una sección obligatoria al final de su prompt:

> "Al finalizar tu trabajo, escribe un append a `.quality/evidence/{feature}/phase_outputs.jsonl` con tu reporte estructurado siguiendo el schema documentado en `doc/specs/phase-outputs-spec.md`."

Helper Python `server/implement_context/phase_outputs.py`:
- `append_phase_output(feature_slug, payload)` — atómico (open w/ append flag)
- `read_phase_outputs(feature_slug) -> list[dict]`
- `aggregate_for_spec_sync(feature_slug) -> dict` — devuelve el shape que espera `write_implementation_status`.

**Spec-Code Sync** (Paso 5.1.1b y 8.5.1a) cambia: en lugar de leer `git diff` desde el contexto del orquestador, llama a `aggregate_for_spec_sync(feature_slug)` y de ahí construye la sección `## Implementation Status` del PRD. Esto sobrevive a Tasks aislados porque cada Task ya escribió su línea.

**Spec contract**: `doc/specs/phase-outputs-spec.md` con frontmatter, ejemplos válidos/inválidos, validador zero-deps.

### 3.6 Telemetría en heartbeat (O6)

`heartbeat-sender.mjs` añade un nuevo bloque DESPUÉS del bloque Stitch Autopilot (que es DESPUÉS del bloque Session Continuity):

```js
// v5.32.0 — Implement Task Isolation: surface task isolation health.
let taskIsolation = null;
try {
  const cachePath = '.quality/task_isolation.json';
  if (fileExists(cachePath)) {
    const t = readJsonFile(cachePath);
    taskIsolation = {
      enabled: t.enabled === true,
      tasks_run_total: t.tasks_run_total ?? 0,
      tasks_failed_budget: t.tasks_failed_budget ?? 0,
      tasks_failed_ownership: t.tasks_failed_ownership ?? 0,
      last_feature_slug: t.last_feature_slug ?? null,
    };
  }
} catch { /* ignore */ }
```

Cache `.quality/task_isolation.json` se escribe por:
- `context-budget-guard.mjs` (incrementa `tasks_failed_budget`).
- `file-ownership-guard.mjs` (incrementa `tasks_failed_ownership`).
- SKILL.md tras cada Task completado (incrementa `tasks_run_total` y actualiza `last_feature_slug`).

## 6. Riesgos y mitigaciones

| Riesgo | Probabilidad | Impacto | Mitigación |
|--------|-------------|---------|------------|
| Estimador chars/4 difiere demasiado del conteo real | MEDIA | BAJO | Margen del 20% en `task_budget_tokens=16000` (vs ideal de 20k). Si se queda corto, telemetría lo mostrará y se promueve a llamada async a Anthropic API en un patch. |
| `active_agent.json` queda huérfano si Task crashea | MEDIA | BAJO | Hook `on-session-end.mjs` lo limpia si tiene >2h. Adicionalmente, el SKILL.md hace `try/finally` para borrar siempre. |
| Ownership map cambia y rompe el guard | BAJA | BAJO | El guard parsea el `.md` en cada invocación; no hay cache. Si la tabla está mal formada, se loguea WARNING y se deja pasar el Write (degradación graceful). |
| Algunos proyectos legacy escriben a `phase_outputs.jsonl` con shape distinto | MEDIA | MEDIO | Validador rechaza líneas sin `schema_version` y `aggregate_for_spec_sync` las skipea con WARNING. La línea queda registrada pero no afecta al PRD. |
| Tasks aislados no heredan auth/MCP del orquestador | MEDIA | ALTO | Documentar en SKILL.md que Tasks heredan automáticamente las tools del padre (cómo lo hace Claude Code), pero NO heredan secretos de prompt. Confirmar con prueba E2E manual antes de promover a strict. |
| El SKILL.md crece demasiado y se vuelve ilegible | BAJA | BAJO | El nuevo "Paso 5.X.0" es un bloque reusable de 6 líneas, no se duplica por fase. |

## 8. Rollback plan

Si v5.32.0 introduce regresiones graves:

1. **Toggle global**: `settings.local.json` → `specbox.implement.task_isolation.enabled: false` revierte al comportamiento v5.31.
2. **Per-guard toggle**: `task_budget_mode: "off"` y `ownership_mode: "off"` desactivan los hooks individualmente.
3. **`execution_context.json` y `phase_outputs.jsonl` se quedan**: no se borran del filesystem; los hooks legacy los ignoran.
