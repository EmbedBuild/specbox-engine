## 1. Constraint arquitectónico: BLOCKER FreeForm + VPS MCP

### Problema verificado

`server/backends/freeform_backend.py` línea 117: `self.root = Path(root)`.
Si el cliente llama `set_auth_token(root_path="doc/tracking")` y el MCP corre en un VPS, `Path("doc/tracking")` se resuelve relativo al CWD del **proceso del VPS**, no del repo del cliente. Resultado:

- Datos se escriben en el filesystem del VPS, no del cliente.
- Multi-tenant: distintos clientes con `root_path="doc/tracking"` colisionan en el mismo path del VPS.
- Silent failure: el cliente cree que está guardando localmente.

### Decisión arquitectónica

FreeForm es **client-side por diseño**. Los datos son del cliente, no del servidor. La elección correcta es **Opción B + medio-A**:

- **Validar en `set_auth_token`**: si `backend_type="freeform"` y el cliente está hablando con un MCP remoto (env `SPECBOX_ENGINE_MCP_URL` no nulo), exigir `root_path` absoluto.
- **Validar absolutez del path**: rechazar paths relativos para FreeForm cuando MCP es remoto.
- **Documentar y guiar**: el skill que onboardea proyectos detecta el modo y construye la ruta absoluta automáticamente desde el cwd del cliente.

Esto requiere que **algún componente client-side conozca el cwd absoluto y lo pase al MCP** al hacer `set_auth_token`. Buenas noticias: hooks como `heartbeat-sender.mjs` ya envían rutas absolutas, así que el cliente sí sabe su path.

### Implementación del fix

**UC-FF-01 — Path validation en FreeformBackend**

`server/backends/freeform_backend.py`:

```python
def __init__(self, root: str):
    p = Path(root)
    if not p.is_absolute():
        raise FreeformPathError(
            f"FreeformBackend requires an absolute path, got: {root!r}. "
            f"When running with a remote MCP, the client must pass the "
            f"absolute path of the project root. Hint: use `cwd_abs/doc/tracking`."
        )
    self.root = p
```

**UC-FF-02 — `set_auth_token` enforcement**

`server/tools/spec_driven.py` función `set_auth_token`:

```python
if backend_type == "freeform":
    root = root_path or "doc/tracking"
    if not Path(root).is_absolute():
        return {
            "ok": False,
            "error": "freeform_path_must_be_absolute",
            "message": "FreeForm backend requires an absolute root_path. "
                       "Pass the project root absolute path (e.g., /Users/me/myproject/doc/tracking).",
            "suggestion": "Use the /app-init skill which auto-detects your absolute path."
        }
    backend = FreeformBackend(root=root)
    await store_freeform_credentials(ctx, root)
```

**UC-FF-03 — Client-side helper para construir ruta absoluta**

`.claude/hooks/freeform-path-resolver.mjs` (nuevo helper, no hook):

```javascript
import path from "node:path";
import { execSync } from "node:child_process";

export function resolveFreeformPath(relativeOrAbsolute) {
  if (path.isAbsolute(relativeOrAbsolute)) return relativeOrAbsolute;
  const cwd = execSync("git rev-parse --show-toplevel", { encoding: "utf8" }).trim();
  return path.join(cwd, relativeOrAbsolute);
}
```

Usado por el skill `/app-init` y por cualquier wrapper que llame `set_auth_token`.

**UC-FF-04 — Multi-tenant isolation guard**

`FreeformBackend.__init__`: añadir verificación de no-collision:

- Antes de escribir, registrar `root` en `STATE_PATH/freeform_registry.json` con timestamp + project_name.
- Si dos sesiones distintas reclaman el mismo `root`, advertir (logging) — no bloquear porque puede ser legítimo (mismo usuario, dos sesiones).

### Acceptance criteria del BLOCKER fix

- **AC-FF-01**: `FreeformBackend("doc/tracking")` lanza `FreeformPathError`.
- **AC-FF-02**: `set_auth_token(backend_type="freeform", root_path="doc/tracking")` desde cliente con MCP remoto retorna `ok=False` con mensaje accionable.
- **AC-FF-03**: `set_auth_token(backend_type="freeform", root_path="/Users/x/proj/doc/tracking")` funciona idéntico a hoy.
- **AC-FF-04**: Proyectos v5.28 con FreeForm + MCP local **siguen funcionando** (la validación solo aplica cuando el cliente pasa relativo, lo cual hoy es el default — necesita migración guiada).

### Migración para FreeForm pre-existentes

Crítico: hay proyectos v5.28 que ya usaron `root_path="doc/tracking"` (relativo). Hay dos sub-casos:

| Sub-caso | Detección | Comportamiento v5.29 |
|----------|-----------|----------------------|
| MCP local + FreeForm relativo | `SPECBOX_ENGINE_MCP_URL` no set | Sigue funcionando (relativo OK localmente). Warning informativo "considera migrar a path absoluto para futura compatibilidad VPS". |
| MCP remoto + FreeForm relativo | `SPECBOX_ENGINE_MCP_URL` set | **Bloqueante en escritura**. Skill `/app-init` ofrece auto-fix migrando settings.local.json al path absoluto. Lectura sigue siendo posible si los datos están en VPS, con warning de "tus datos viven en VPS, no en tu repo — `/app-init --migrate-freeform-data` los baja al repo". |

### Implementación técnica

**Helper compartido `lib/autopilot.mjs`**:

```javascript
export async function shouldAutoConfirm(decisionKey, context = {}) {
  const config = await loadAutopilotConfig(context.projectPath);
  const policy = AUTOPILOT_POLICY[config.level] || AUTOPILOT_POLICY.low;
  const rule = policy[decisionKey];
  if (!rule) return { autoConfirm: false, reason: "unknown_decision_key" };
  const result = await rule.evaluate(context);
  if (result.autoConfirm) {
    await logAutoDecision(decisionKey, result, context);
  }
  return result;
}
```

Cada uno de los 17 puntos en los SKILL.md llama este helper antes de preguntar. Si retorna `autoConfirm: true`, el skill avanza con el default + log; si `false`, pregunta como hoy.

## 4. Capa 3 — Cola diferida `decisions_queue.md`

### Filosofía

Un gate puede tener uno de tres comportamientos:

1. **Síncrono bloqueante** (hoy, sigue siendo así para destructivos): pregunta y para hasta respuesta.
2. **Auto-confirm** (Capa 2): aplica default razonable y sigue.
3. **Diferido** (nuevo, Capa 3): registra la pregunta en cola, aplica default tentativo, sigue trabajando, espera feedback humano antes de marcar el UC como completo.

Diferido aplica a decisiones cuyo default es **suficientemente bueno para continuar pero no tan crítico que requiera bloquear**.

### Layout

`doc/app/decisions_queue.md`:

```markdown
# Decisions Queue — {project_name}

## Pendientes

### [feature: signup-flow] [uc: UC-003] veg_preview
- **Generado:** 2026-05-02 14:30:12
- **Default aplicado:** Modo Per-ICP arquetipo Startup (score=0.82)
- **Bloquea:** marcar UC-003 como ACCEPTED hasta resolución
- **Acción:** confirmar | ajustar | revertir
- **Evidencia:** doc/veg/signup-flow/preview.md
- **Engine ID:** dq-2026-0502-1430-12-veg

### [feature: dashboard] [uc: UC-007] image_cost_under_budget
- **Generado:** 2026-05-02 15:10:08
- **Default aplicado:** Generadas 4 imágenes por €3.20
- **Bloquea:** ninguno (auto-confirmado, registrado para revisión)
- **Acción:** revisar | aprobar | revertir
- **Engine ID:** dq-2026-0502-1510-08-img

## Resueltas (últimas 7 días)

### [feature: login] [uc: UC-001] tokens_confirmation
- **Resuelto:** 2026-05-01 09:15 — confirmado
- **Engine ID:** dq-2026-0501-0915-tok
```

### Skill `/queue review`

`context: direct`. Acciones:

- Lista todas las pendientes (cross-feature, cross-project si se invoca con `--all-projects`).
- Permite resolver en batch: `/queue review --approve-all-veg-above 0.85`.
- Tras resolución, los UCs bloqueados se desbloquean automáticamente.
- Auto-resolve después de N días configurable (`autopilot.queue_auto_resolve_days`, default 7) con default tentativo, dejando log auditable.

### Cuándo NO usar la cola

- Acciones destructivas → siempre síncrono.
- Definition Quality Gate fallido → siempre síncrono (sin AC no hay siguiente paso).
- Presupuesto monetario excedido sin alternativa razonable → siempre síncrono.

### Acceptance criteria Capa 3

- **AC-L3-01**: Decisión deferrable se acumula en `decisions_queue.md`.
- **AC-L3-02**: UC con decisión diferida no se marca ACCEPTED hasta resolución.
- **AC-L3-03**: `/queue review` lista pendientes y permite resolución batch.
- **AC-L3-04**: Auto-resolve después de N días deja entrada en `Resueltas` con flag `auto_resolved: true`.
- **AC-L3-05**: Acciones destructivas nunca llegan a la cola.

## 5. Capa 4 — Decisiones canónicas en Engram

### Mecanismo

Cuando el usuario confirma una decisión 3 veces consecutivas idénticas para el mismo `decision_key` en el mismo proyecto, el engine ofrece "convertirla en canónica":

```
He notado que has confirmado VEG arquetipo "Startup" 3 veces seguidas en este proyecto.
¿Convertir en decisión canónica? [Sí: nunca repreguntar | No | Solo en este proyecto]
```

Si confirma, se guarda como observación Engram con:

- `topic_key: "autopilot/{project_name}/{decision_key}"`
- `type: "decision"`
- Contenido: valor + razón + timestamp + scope (project | personal)
- Espejo en `app_spec.md sección 6` para visibilidad humana.

### Cómo se consume

Cada skill, antes de aplicar política autopilot:

1. `mem_search(topic_key="autopilot/{project}/{decision_key}")` — si hit, usa el valor canónico sin preguntar.
2. Solo si miss → política autopilot.
3. Solo si autopilot dice ask → pregunta al usuario.

### Invalidación

- Si el usuario edita manualmente `app_spec.md sección 6`, la entrada Engram se actualiza.
- Si cambia algo del proyecto que invalida la decisión (ej: cambio de stack), el engine pregunta una vez más para revalidar.
- Comando `/queue review --revoke-canonical {decision_key}` para revertir explícitamente.

### Acceptance criteria Capa 4

- **AC-L4-01**: 3 confirmaciones idénticas consecutivas disparan oferta de canonicalización.
- **AC-L4-02**: Decisión canónica se reutiliza sin preguntar en sesiones futuras.
- **AC-L4-03**: Decisión canónica aparece en `app_spec.md sección 6`.
- **AC-L4-04**: Cambio en stack invalida decisiones canónicas relacionadas y dispara revalidación.

- Preserva: items, ACs, comments, attachments (descargados localmente).

## 12. Capa 5 — Sync enforcement: retroalimentación bidireccional `app_*.md` ↔ realidad

### 12.1 Principio rector

`app_prd.md` y `app_spec.md` solo son útiles si la realidad del proyecto los refleja **continuamente**. Sin retroalimentación enforced, en 2-3 sprints se convierten en mentira documentada y dejan de ser fuente de verdad.

La estrategia es **push-based con guardrails bloqueantes en eventos pivote**: el engine sincroniza automáticamente tras cada evento que muta el spec real, y los hooks **bloquean operaciones** si la sincronización no se ejecutó. No hay best-effort: o el sync ocurre, o el siguiente paso del pipeline no avanza.

### 12.2 Modelo de zonas en `app_*.md`

Cada documento se divide en **zonas con políticas distintas**:

```markdown
<!-- @specbox:zone start kind="manual" id="vision" -->
## 1. Visión
{contenido editable por el usuario, jamás tocado por el engine}
<!-- @specbox:zone end -->

<!-- @specbox:zone start kind="auto" id="roadmap" auto_sync_on="complete_uc,move_uc" -->
## 5. Roadmap de US
{contenido reescrito por el engine tras eventos pivote — NO EDITAR A MANO}
<!-- @specbox:zone end -->

<!-- @specbox:zone start kind="hybrid" id="canonical_decisions" auto_sync_on="canonical_decision_created" merge="append_only" -->
## 6. Decisiones canónicas
{usuario puede añadir entradas; engine añade nuevas con append-only; engine nunca borra entradas usuario}
<!-- @specbox:zone end -->
```

Tres tipos de zona:

| `kind` | Propiedad | Quién escribe | Conflicto |
|--------|-----------|---------------|-----------|
| `manual` | Solo el usuario edita. Engine la lee como input pero nunca la modifica. | Usuario | Imposible. |
| `auto` | Solo el engine reescribe. Usuario no debe editar (warning visible en hook si lo hace). | Engine | Si el usuario edita, hook detecta y avisa. Engine sobreescribe en próxima sync. |
| `hybrid` | Append-only. Usuario añade entradas arriba; engine añade abajo con marcador `<!-- engine-entry id=... -->`. | Ambos | Convivencia controlada por marcadores. |

Esto se aplica tanto a `app_prd.md` como a `app_spec.md`. La estructura de zonas viene definida en el template, no es libre.

### 12.3 Eventos pivote que disparan sync (mapping completo)

Cada evento del pipeline tiene una tabla canónica de qué zonas actualiza:

| Evento del pipeline | Tool / hook origen | Zonas afectadas | Modo sync |
|---------------------|--------------------|-----------------|-----------|
| `complete_uc()` | spec_driven tool | `app_prd.md sección 5 Roadmap` (mover UC a "completed"), `app_spec.md sección 6` (si decisión canónica generada) | bloqueante |
| `move_uc()` a estado terminal | spec_driven tool | `app_prd.md sección 5 Roadmap` | bloqueante |
| `mark_ac_batch()` con todos AC=accepted | spec_driven tool | `app_prd.md sección 5 + sección 4 Métricas` (si métrica vinculada) | bloqueante |
| `add_uc()` / `add_us()` | spec_mutations tool | `app_prd.md sección 5 Roadmap` (añadir entrada en "planned") | bloqueante |
| `delete_uc()` / `delete_ac()` | spec_mutations tool | `app_prd.md sección 5 Roadmap`, `app_spec.md sección 6` (si decisión obsoleta) | bloqueante |
| `set_auth_token()` con backend distinto | spec_driven tool | `app_spec.md sección 2 Tracking backend` | bloqueante |
| `/visual-setup` confirma VEG arquetipo | skill | `app_spec.md sección 3 Brand & Visual` | bloqueante |
| `/visual-setup` confirma brand kit | skill | `app_spec.md sección 3` | bloqueante |
| Decisión canónica creada en Engram | autopilot Capa 4 | `app_spec.md sección 6 Decisiones canónicas` | bloqueante |
| Decisión canónica revocada | `/queue review --revoke-canonical` | `app_spec.md sección 6` | bloqueante |
| AG-09b verdict ACCEPTED | acceptance tool | `app_prd.md sección 5 Roadmap` (UC → completed), `app_prd.md sección 4 Métricas` | bloqueante |
| `/feedback` con resolución que cambia AC | feedback tool | `app_prd.md sección 5` (delta documentado), `app_prd.md sección 6` (si afecta stakeholder) | bloqueante |
| Stack change detectado (nuevo lockfile, nuevo framework) | drift detector | `app_spec.md sección 1 Stack` | warning + propuesta |
| Multirepo role change | settings | `app_spec.md sección 4 Convenciones, subapartado multirepo` | bloqueante |
| Release version bump | `/release` skill | `app_spec.md sección 1 + meta`, `CHANGELOG` | bloqueante |
| `image_budget` modificado en settings | autopilot config | `app_spec.md sección 5 Autopilot` | bloqueante |

**"Bloqueante"** = el tool/skill que originó el evento NO RETORNA ÉXITO hasta que la sincronización del documento canónico se ha confirmado. Esto hace imposible que el spec real avance sin que `app_*.md` lo refleje.

### 12.4 Implementación técnica del enforcement

#### 12.4.1 Tool wrapper `app_sync.py`

Nuevo módulo `server/tools/app_sync.py` con:

- `sync_app_docs(project_path, event_type, payload)` — sync atómico tras evento.
- `verify_app_docs_in_sync(project_path)` — devuelve `{in_sync: bool, drift: [...]}`.
- `compute_app_docs_signature(project_path)` — hash determinista del estado proyectado vs estado documentado.
- `detect_zone_violations(file_path)` — escanea zonas `auto` y detecta ediciones manuales.

#### 12.4.2 Decoradores en tools que mutan el spec

Cada tool en `spec_driven.py` y `spec_mutations.py` que dispara un evento pivote se decora:

```python
@requires_app_docs_sync(event_type="complete_uc")
async def complete_uc(...):
    # 1. ejecuta lógica original
    result = await _complete_uc_inner(...)
    # 2. el decorador llama a sync_app_docs antes de retornar
    # 3. si sync falla, el tool devuelve error y el cliente sabe que el spec quedó inconsistente
    return result
```

El decorador es **transactional**: si la lógica del tool tiene éxito pero el sync falla, el tool retorna `{ok: false, error: "app_docs_sync_failed", ...}` y el caller debe reintentar o invocar `/app-sync --repair`. **Nada continúa hasta que el sync se confirme.**

#### 12.4.3 Hook bloqueante `app-docs-sync-guard.mjs` (nuevo)

`PostToolUse` para tools que mutan spec + `PreToolUse(git commit)`:

- Antes de cada commit, llama `verify_app_docs_in_sync()`.
- Si retorna `in_sync: false` → BLOCKING con mensaje:
  ```
  ❌ app_docs_out_of_sync
  Detected drift between code state and doc/app/app_*.md:
   - UC-007 marked completed in tracking but app_prd.md sección 5 still lists as "in_progress"
   - VEG arquetipo "Startup" used in features/* but app_spec.md sección 3 declares "Corporate"

  Run /app-sync --repair to reconcile, or /app-sync --review to inspect drift.
  ```
- No bypass posible (`--no-verify` ya está bloqueado por `no-bypass-guard.mjs` v5.18+).

#### 12.4.4 Hook informativo `app-docs-edit-warning.mjs`

`PostToolUse(Write|Edit)` cuando el archivo tocado es `app_prd.md` o `app_spec.md`:

- Si la edición cae dentro de una zona `auto` → WARNING (no bloquea, pero informa al usuario que su edición será sobrescrita en próxima sync).
- Si cae en zona `manual` o `hybrid` → silencioso.

Esto da al usuario una señal clara cuando está editando algo que no debería.

#### 12.4.5 Skill `/app-sync` (nuevo)

`context: direct`. Subcomandos:

- `/app-sync --check` → reporta drift sin tocar nada (útil en CI).
- `/app-sync --repair` → recomputa zonas `auto` desde la realidad del proyecto, propone diff, espera confirmación, aplica.
- `/app-sync --review` → modo interactivo: lista cada delta detectado, usuario decide caso por caso.
- `/app-sync --rebuild-from-tracking` → escenario emergencia: regenera `app_prd.md` desde cero leyendo `doc/tracking/` y `app_spec.md` desde cero leyendo settings + git history.

Este skill es la única forma legítima de "saltarse" el bloqueo del hook `app-docs-sync-guard`: si el usuario ejecuta `/app-sync --repair`, el guard hash se actualiza y el siguiente commit pasa.

### 12.5 Drift detection multi-fuente

Más allá de eventos del pipeline (que son determinísticos y disparables por hook), hay **drift implícito** que requiere detector activo:

| Tipo de drift | Detector | Frecuencia |
|---------------|----------|------------|
| Stack change (nuevo lockfile, nuevo `pubspec.yaml`, nuevo `package.json`) | hook `git commit` que escanea archivos modificados de tooling | cada commit |
| AC en código no listado en `app_prd.md sección 5` | analyzer en `verify_app_docs_in_sync` | cada commit + cada `/implement` |
| Decisión canónica usada en código pero no en `app_spec.md sección 6` | grep cross-reference | cada `/implement` |
| Roadmap sección 5 declara feature como "completed" pero ningún UC tiene verdict ACCEPTED | tool `verify_app_docs_in_sync` | cada `/implement` |
| Brand kit referenciado en `app_spec.md sección 3` no existe en filesystem | path validation | cada `/visual-setup` y cada commit |

El detector vive en `server/audit/app_docs_drift.py` (nuevo, reutiliza patrones de `server/audit/analyzers/`). Se ejecuta:

- **Síncronamente** en `verify_app_docs_in_sync()` antes del bloqueo de commit.
- **Asíncronamente** en heartbeat → reporta drift al VPS para que aparezca en Sala de Máquinas.

### 12.6 Retroalimentación a Engram

Cada sync exitoso emite una observación Engram:

- `topic_key: "app_docs_sync/{project}/{event_type}"`
- `type: "sync"`
- Contenido: evento + zonas modificadas + hash anterior y nuevo + timestamp.

Esto da:

- Auditabilidad histórica (¿cuándo se actualizó por última vez sección 5?).
- Detección de proyectos abandonados (sin sync en 30 días = warning).
- Capacidad de `/app-sync --rebuild-from-tracking` para reconstruir desde Engram si los archivos se corrompen.

### 12.7 Caso especial: edición manual del usuario en zona `auto`

Cuando `app-docs-edit-warning.mjs` detecta que el usuario está editando una zona `auto`, NO bloquea (no queremos prohibirle editar su propio archivo). Pero registra la edición en `.quality/manual_edits_in_auto_zones.jsonl` y el siguiente `verify_app_docs_in_sync` tratará la zona como **no canónica hasta que el usuario reconcilie**:

```
Hook detected manual edit in auto-zone "roadmap" of app_prd.md.
Auto-sync is paused for this zone until you decide:
 [a] keep my edits — convert zone to manual (you maintain it)
 [b] discard my edits — let engine resync from tracking
 [c] merge — show diff and let me reconcile
```

Esto da al usuario soberanía total mientras mantiene la integridad sistemática.

### 12.8 Comando de inicialización idempotente

`/app-init --upgrade-zones` para proyectos con `app_*.md` pre-existentes (creados manualmente o en versiones tempranas sin estructura de zonas):

- Detecta secciones existentes.
- Propone mapping a `manual` / `auto` / `hybrid` según contenido inferido.
- Inserta marcadores `<!-- @specbox:zone -->`.
- Pide confirmación antes de reescribir.

| Riesgo | Probabilidad | Impacto | Mitigación |
|--------|--------------|---------|------------|
| Sync bloquea commits legítimos por falso positivo de drift | Media | Alto | `/app-sync --check` ejecutable manualmente para diagnóstico; hash signature determinista evita races; ventana de 5 min de gracia tras sync exitoso. |
| Usuario edita zona `auto` y pierde su trabajo en próxima sync | Media | Alto | Hook `app-docs-edit-warning.mjs` avisa inmediatamente; pausa de auto-sync hasta reconciliación explícita; backup en `.quality/edits_backup/` antes de cualquier overwrite. |
| Sync transactional falla a media tool (UC marcado pero app_prd no actualizado) | Baja | Crítico | Decorator implementa rollback: si sync falla, intenta revert del cambio original; si no puede, deja proyecto en estado `pending_sync` que `/app-sync --repair` resuelve. |
| Drift detector tiene falsos positivos por archivos no relacionados | Media | Medio | Whitelist explícita de qué archivos contribuyen a stack/spec detection; configurable en `app_spec.md sección 4`. |
| Performance impact en proyectos grandes (sync en cada commit) | Baja | Medio | Cache de signature en `.quality/app_docs_sync.lock`; hash incremental; sync solo escanea zonas afectadas por evento (no todo el doc). |
| Hooks de sync conflictúan con hooks existentes (spec-guard, e2e-gate) | Media | Alto | Hooks ordenados explícitamente en `settings.json`; tests E2E con todos los hooks activos sobre fixtures. |

### 12.12 Pregunta abierta sobre Capa 5

**¿Habilitamos Capa 5 con bloqueo desde día 1 o con modo "warning-only" durante 1 semana?**

- **Bloqueo día 1** (recomendado): garantía de calidad inmediata, pero arriesga que un bug en sync paralice el pipeline.
- **Warning-only 1 semana**: hooks reportan drift pero no bloquean, permite detectar bugs reales sin paralizar trabajo. Activación de bloqueo en v5.29.1.

Mi recomendación: **warning-only la primera semana** + bloqueo desde v5.29.1. Capa 5 es la más invasiva y puede tener edge cases que solo emergen en proyectos reales. Mejor descubrirlos sin paralizar el desarrollo.
